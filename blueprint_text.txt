Every prediction is accompanied by SHAP-driven explanations, actionable clinical recommendations, and a downloadable PDF report — enabling clinicians and patients to understand not just what the model predicts, but why. 1.2 Business Problem Chronic diseases (diabetes, cardiovascular disease, hypertension) account for over 74% of global deaths annually. Primary care physicians face time constraints that reduce preventive screening quality. Patients lack tools to self-monitor multi-disease risk from home. Existing EHR-embedded models are black boxes that erode clinician trust. Core Problem Statement There is no accessible, explainable, multi-disease risk tool that a GP can deploy in under 5 minutes, that a patient can operate without medical literacy, and that produces evidence-grade audit trails for clinical governance. 1.3 User Personas Persona Role Goals Pain Points Dr. Riya Patel Primary Care Physician Quick risk screening during 10-min consultations EHR models We map each patient record to one of four labels: Diabetes (0), Heart Disease (1), Hypertension (2), Healthy (3). The model must handle overlapping clinical features across diseases (e.g., BMI and blood pressure appear in all three), so a unified feature space across merged datasets is essential. 3.2 Public Random Forest · XGBoost · Ensemble 5.1 Why Three Base Models + Ensemble Each algorithm has complementary inductive biases. Decision Trees provide interpretable splitting logic. Random Forest reduces variance through bagging. XGBoost reduces both bias and variance through gradient boosting. Ensemble voting combines their posterior probabilities, empirically outperforming any single base model on tabular medical data. 5.2 Model Configurations 5.2.1 Decision Tree (Baseline + Global &amp; Local Explanations 7.1 Why SHAP SHAP (SHapley Additive exPlanations) provides game-theory-grounded attribution of each feature to the prediction output. Unlike LIME (which is unstable) or attention weights (which are model-specific), SHAP satisfies consistency, dummy, and efficiency axioms. TreeExplainer is O(TLD²) for tree models, making it tractable for real-time clinical use. 7.2 SHAP Integration Architecture from shap import TreeExplainer, Explanation # Initialised once at app startup (model loaded into memory) explainer = TreeExplainer(ensemble.named_estimators_[&quot;rf&quot;]) # Note: use RF sub-model for SHAP — VotingClassifier has no native SHAP # RF SHAP values closely mirror ensemble behaviour def explain_local(X_single: np.ndarray) -&gt; dict:     shap_values = explainer.shap_values(X_single)  # shape: (n_classes, n_features)     top5_idx = np.argsort(np.abs(shap_values[pred_class]))[-5:][::-1]     return {         &quot;feature_names&quot;: [feature_names[i] for i in top5_idx],         &quot;shap_values&quot;:   [float(shap_values[pred_class][i]) for i in top5_idx],         &quot;base_value&quot;:    float(explainer.expected_value[pred_class]),     } 7.3 Global SHAP Explanations Computed on a random stratified sample of 500 training records at model training time Stored as a precomputed summary JSON in MongoDB (global_shap collection) Refreshed every time model is retrained Served via GET /analytics/shap-global to admin dashboard 7.4 Local SHAP Explanations Computed live for each patient prediction (latency contribution &lt; 150 ms) Waterfall chart data (feature, SHAP value, feature value) returned in prediction response Frontend renders interactive bar chart coloured red (increases risk) / blue (reduces risk) 7.5 Explanation Output Schema {   &quot;base_value&quot;: 0.42,   &quot;predicted_class&quot;: &quot;Diabetes&quot;,   &quot;predicted_prob&quot;:  0.78,   &quot;shap_contributions&quot;: [     {&quot;feature&quot;: &quot;glucose&quot;,       &quot;value&quot;: 210, &quot;shap&quot;: +0.31, &quot;direction&quot;: &quot;risk&quot;},     {&quot;feature&quot;: &quot;hba1c&quot;,         &quot;value&quot;: 8.2, &quot;shap&quot;: +0.18, &quot;direction&quot;: &quot;risk&quot;},     {&quot;feature&quot;: &quot;bmi&quot;,           &quot;value&quot;: 29,  &quot;shap&quot;: +0.09, &quot;direction&quot;: &quot;risk&quot;},     {&quot;feature&quot;: &quot;physical_act&quot;,  &quot;value&quot;: 1.5, &quot;shap&quot;: -0.07, &quot;direction&quot;: &quot;protective&quot;},     {&quot;feature&quot;: &quot;age&quot;,           &quot;value&quot;: 52,  &quot;shap&quot;: +0.05, &quot;direction&quot;: &quot;risk&quot;}   ] } SECTION 08 Risk Scoring Engine Severity Levels, Thresholds, Formulas 8.1 Risk Score Formula The raw probability from the ensemble (P) is adjusted by a severity weighting that reflects the clinical danger of the predicted disease. Heart Disease carries the highest mortality weight. Disease Weight (W):   Heart Disease  → W = 1.20   Diabetes       → W = 1.10   Hypertension   → W = 1.05   Healthy        → W = 1.00 Risk Score (RS) = min(P × W × 100, 100) RS ∈ [0, 100] 8.2 Severity Level Thresholds Severity Level Risk Score Range Colour Action Low Risk RS &lt; 30 Green (#16A34A) Monitor annually; lifestyle tips Medium Risk 30 ≤ RS &lt; 55 Yellow (#CA8A04) 6-month follow-up; moderate intervention High Risk 55 ≤ RS &lt; 80 Orange (#EA580C) 3-month follow-up; clinical referral Critical Risk RS ≥ 80 Red (#DC2626) Immediate GP consultation; urgent action 8.3 Severity Calculation Workflow def compute_risk(probabilities: dict, primary_class: str) -&gt; RiskResult:     P = probabilities[primary_class]          # max probability     W = DISEASE_WEIGHTS[primary_class]     RS = min(P * W * 100, 100)     severity = (         &quot;Low&quot;      if RS &lt; 30 else         &quot;Medium&quot;   if RS &lt; 55 else         &quot;High&quot;     if RS &lt; 80 else         &quot;Critical&quot;     )     return RiskResult(score=RS, severity=severity, color=COLOR_MAP[severity]) 8.4 Multi-Disease Overlay (Comorbidity Warning) If any non-primary disease probability &gt; 0.35, a comorbidity alert is raised. For example: primary = Diabetes (0.72), Heart Disease = 0.38 → alert: &quot;Elevated cardiovascular risk co-exists. Lipid panel recommended.&quot; SECTION 09 Recommendation Engine Rule-Based Clinical Advice per Disease and Severity 9.1 Design Principles Deterministic rule engine — no LLM generation to avoid hallucinated medical advice Rules are stored in a structured YAML config file (version-controlled, auditable) Rules are indexed by: (primary_disease, severity, feature_flags) Feature flags: is_smoker, is_obese, is_elderly (age&gt;65), has_family_hx 9.2 Recommendation Schema {   &quot;disease&quot;:    &quot;Diabetes&quot;,   &quot;severity&quot;:   &quot;High&quot;,   &quot;lifestyle&quot;:  [&quot;Reduce refined carbohydrate intake&quot;, &quot;7–8 hours sleep nightly&quot;],   &quot;diet&quot;:       [&quot;Mediterranean diet pattern&quot;, &quot;Glycaemic index &lt; Risk Delta 10.1 Architecture The What-If engine re-uses the exact same preprocessing pipeline and ensemble model.
